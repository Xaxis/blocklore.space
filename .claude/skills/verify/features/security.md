# Security

A reader sees every known way Bitcoin can be attacked, by layer, with its live status, the published claims that explain and defend against each, the projects' advisories filed under each (with the rule that filed it), each threat's CVE ids checked against NVD, the watches' readings, the lab's run on the newest release of each maintained Bitcoin Core major (newest first) and the newest advisories; an assistant reads the same through the `threats` and `watches` MCP tools.

## Sub-features

- data: `bundle.security` (a `SecurityView` compiled by `core/src/security.ts` from `knowledge/security/threats/`, `watches.json`, `lab.json`, `advisories.json` and `advisory-map.yaml`), read through `web/lib/security.ts` (server-only: `security`, `allThreats`, `getThreat`, `watchById`, `claimsOf`, `securityScene`). The pure queries the MCP tools use are in `core/src/threatmap.ts` (`@blocklore/core/threatmap`).
- map (`/security`, `web/app/security/page.tsx`): the plain lede, counts in the header meta, a strip with one segment per threat in map order, the three statuses each with a one-line meaning, then every layer in `LAYERS` order with its counts and its threats. A threat row: status chip (a shape per status, so it reads without color: square defended, half watching, ring open), title linking to `/security/<id>`, published claim count (left out at zero), "being researched" when claims or mitigations are missing, watch count, lab tests ("lab N of M passing on K releases", counting a test as passing when it passed on every release that ran it, or "not run yet"), "raised by a watch".
- watches: one line per watch (title, a line of context from its data, value in its unit, a sparkline of its history, status chip); opening one shows what it measures, its documented thresholds (`WATCHES` in `core/src/watch.ts`), its source and when it was read. Empty state when `watches.json` has no readings.
- lab (BACKLOG 40): `bundle.security.labReleases` (`labReleases` in `core/src/security.ts`: of each of the newest `MAINTAINED_MAJORS` = 3 majors in `lab.json`, the run on its newest release, newest release first) as a line per release (`LabReleases` in `web/components/security/parts.tsx`, the design system's `.lines`, so nothing scrolls sideways in the narrow column beside the scene): "Bitcoin Core 32.1" with a badge "50 of 50 tests passed", then when it ran, "Matched SHA256SUMS", "8 of 40 builder signatures good", "libsecp256k1's own tests: 3 of 3 programs passed" (only when the run has `secp256k1/` tests) and how long the tests took; below them the machine, "Bitcoin Core's tests 3 at a time, libsecp256k1's one by one" and that an older release runs only the tests it has. The lede names libsecp256k1's test programs. The header meta says "Lab: Bitcoin Core 32.1, 31.3 and 30.5". Empty state "The lab has not published a run yet". `labRuns` keeps every published run for progress and Nostr.
- advisories (BACKLOG 36, `core/src/advisories.ts`): `knowledge/security/advisories.json` (the brain's: every advisory the watch has read, with the CVE and GHSA ids it names, and NVD records) is matched to threats at bundle time by `matchAdvisory` under the owner's `knowledge/security/advisory-map.yaml`, one rule per match, strongest first: `owner` (the map's `assign`; an empty list means on no threat), `record` (the threat's history cites its page), `id` (a CVE or GHSA id the threat's history or terms list), `source` (the map's `sources` files every advisory of a project), `term` (one of the threat's terms in the title), `keyword` (the map's `keywords` in the title); `exclude` takes a threat away. Words match whole, any case (`hasWords`). `/security` shows the 8 newest (title linked, source, date, severity, each CVE id linked to NVD with "in NVD since" or "Not in NVD yet", and "Filed under" its threats or "On no threat yet: an advisory to map"), with "N read, M filed under a threat, K to map" beside the heading. An advisory nothing files and the map does not name is `bundle.security.advisories.unmatched` and `bundle.gaps.advisories` (gaps.md).
- NVD (BACKLOG 38): every CVE id a threat's history or terms name is a `CveCheck` (`checkCve`): `missing` (NVD has no record), `rejected`, `product` (NVD's CPE pairs, CNA data and description name no project the check expects: the map's `expect`, else the projects of advisories that carry it, else the project of the page the history cites it at by the map's `products[].pages`, else any project in `products`), `unnamed` (NVD names nothing the map knows), or none. Findings never change knowledge text.
- report: the rail lists each project's private security contact and policy from `DISCLOSURE` (`core/src/disclosure.ts`).
- threat (`/security/<id>`, `web/app/security/[threat]/page.tsx`): statically generated for every threat, `dynamicParams = false` (an unknown id is 404). Crumbs to the map and the layer, status chip and meaning, which watch raised it when `raisedBy` is set; "What it is" and "What defends against it" as `ClaimLine`s linking `/claims/<id>` (only published claims), each saying "Being researched" and that it is on the brain's research list when it has no published claim (`missing`); its watches with value, context, a wider sparkline, measures, thresholds, source and last read; its lab tests by release (`LabMatrix`: the design system's `.table` in a keyboard-scrollable `TableWrap`, a row per test, a column per release in `labReleases` with its date, each cell Passed, Failed or Not run when that release's run did not have the test, e.g. `p2p_private_broadcast.py` on 30.5; Not run yet when the lab has no run; a row's label is `labTestLabel` in `core/src/security.ts`: the release check in words, `secp256k1/tests` as "libsecp256k1 tests", with a sentence under the heading saying what the libsecp256k1 rows are when the threat has them, as `signature-library` and `nonce-reuse` do); "Its advisories" (`#advisories`, shown when it has any or lists the advisories watch): each advisory with source, date, severity, CVE ids against NVD, and the sentence of the rule that filed it ("Filed here because this threat's public record cites its page.", "...record names CVE-...", "...with every advisory LND publishes...", or "Matched by words in its title: <q>memory DoS</q>, ..." for a term or keyword); "Checked against NVD" (`#nvd`, when its record names CVE ids): a callout "N findings for the owner: ids" and per id a badge (Matches, Not checked yet, No NVD record, Rejected by NVD, Another product, Product unclear), "In NVD since", what NVD says it affects (vendor:product), the projects it names, where the threat names it, when checked, and "For the owner: ..." per finding; its public record (`history` refs linked, host and date, and a CVE ref's NVD date or "see the NVD check"); the rail links its topic and its layer.
- scene: `securityScene()` in `web/lib/security.ts` gives `SceneData["security"]` (layers, threats with live status) for the scene's security layer.
- mcp: `threats` (`id`, `layer`, `status`, all optional) and `watches` (`id` optional) in `web/lib/mcp.ts`; see mcp.md for the driver. `watches` carries `lab` (`labReport` in `core/src/threatmap.ts`: each maintained release's run, newest first, with when, platform, verified, jobs, seconds, passed of run and each test's result). A threat in the list carries `lab` (`labCounts`: tests, run, passed, and passed of run per release); one threat carries `lab` (`threatLab`: each test with `releases`, ok null where that release's run did not have it). The list carries `advisories` per threat and `nvd_findings`, and a top-level `advisories` summary (`advisorySummary`: counts and `to_map`); one threat carries `advisories` (`threatAdvisories`: each with `filed_by {rule, matched, by_words}` and its NVD states) and `nvd` (`cveCheck`: state, status, published, affects, names, expected, finding, mismatch).

## The brain's side: watches, lab, embargo

- watches (`pnpm brain watch`, `brain/src/security/watches.ts`; readings and thresholds in `core/src/watch.ts`): each due watch (or all with `--force`, one with `--only <id>`) reads public data through `brain/src/http.ts`, stamps a reading into `knowledge/security/watches.json` (status ok, elevated, alert or unknown; a short history) and logs a `watch` event per status change to the public feed log `var/control/feed.jsonl` (through `logEvent` in `brain/src/security/events.ts`; the daemon sends it to the site, the front page shows it as "Watching"). Blocks come from mempool.space and blockstream.info, which must agree on every id, time, target and version, read side by side in pages aligned to each one's size; `var/security/blocks.json` follows the last 160 blocks for reorgs and keeps each version of the tip's difficulty period and the one before, for the version bits (`brain/src/signaling.ts`, see [proposals](proposals.md)), whose `knowledge/chain/signaling.json` rides in the same commit. The hourly tick runs `watch({ force: false, commit: true })`.
- lab (`pnpm brain lab [--version 31.3,30.5]`, `brain/src/security/lab.ts`): the newest point release of each maintained Core major (`maintainedReleases` over `git ls-remote --tags`; a major with only rc tags is not out), or the versions named, one after another; for each, `SHA256SUMS` and builder signatures checked, that release's functional tests mapped to threats (only those it has; the rest printed as left out) run in regtest against its binaries (`-j` modest) under `heavy`, then libsecp256k1's own test programs the map names (`secp256k1/tests`, `secp256k1/noverify_tests`, `secp256k1/exhaustive_tests`; `selectTests` keeps them apart from the scripts) built from that release's `src/secp256k1` and run (below), then the disclosure gate on that release alone. A passing run joins `knowledge/security/lab.json` beside the other releases' runs (`keepLabRuns`: newest first, up to 12 of each major); a failure or a release that did not verify is embargoed and nothing public changes for it. A release that cannot run does not stop the others; the lab fails at the end naming it. It ends with one line per release: result, passed of run, the tests' seconds and the whole run's. One commit for everything published. The weekly tick runs `lab({ publish: true, commit: true })`. Releases before 32.0 write `config.ini.in` components as `@X_TRUE@` line prefixes (`configIni` fills both forms; left unfilled, the runner printed "No functional tests to run" and every test was held as failed). The runner gets `TEST_RUNNER_PORT_MIN` from `portBase`: the first base from 11000 in steps of 1000 whose p2p, RPC (+5000) and proxy (+10000) windows nothing on the machine listens on (`listeningPorts` reads `/proc/net/tcp` and `tcp6`), printed as "lab: test ports from N"; with the framework's default 11000 another project's server on 11600 failed one test per release on 2026-11-23.
- libsecp256k1 (`brain/src/security/secp256k1.ts`, BACKLOG 40): the source tarball is in the release's `SHA256SUMS`, so its `src/secp256k1` is the verified copy the release's binaries were built from. No cmake on the box: `secpBuild` reads the release's `cmake/secp256k1.cmake` (Core's forced modules: ECDH off, recovery and musig on; RelWithDebInfo; hidden visibility), `src/secp256k1/CMakeLists.txt` (module defaults, `ECMULT_WINDOW_SIZE`, the comb for `ECMULT_GEN_KB`, `USE_ASM_X86_64` on x86_64, `-std=c90`, `-O2 -g`) and `src/secp256k1/src/CMakeLists.txt` (module blocks in order with their dependencies, the precomputed tables, each program's source and defines: `VERIFY`, `SUPPORTS_CONCURRENCY=1` from 31.3; 32.1's `add_executable_and_tests` function expanded), and throws on anything it cannot read the same way, which fails the programs like a test. `secpCommands` gives the gcc calls: the precomputed tables as objects, then each program from `tests.c` or `tests_exhaustive.c`. Each gcc call and each program runs as `heavy /usr/bin/time -f %e -o <file> timeout ...` (15 min per build step, 60 min per program, the seconds counted only once it holds a slot) in `<lab>/<v>/secp256k1/`, with no arguments (16 iterations; exhaustive 2). `secpPassed`: exit 0 and the program's own last line ("no problems found", or the unit test framework's "Total execution time: N seconds" from 31.x). Each program is a `LabTest` (`secp256k1/<program>`, its result, its seconds) in that release's run; the run's seconds add them; the private record keeps the gcc commands, build seconds, modules and each program's last 40 lines (with its random seed), and a failed program's lines join the tail the admin shows. A failure or a build error holds the release like any failed test, and the embargo names `secp256k1-security@bitcoincore.org` beside Core's address. The lab prints "lab: libsecp256k1 0.8.1 from Bitcoin Core's src/secp256k1, modules ...", "lab: libsecp256k1 built in N s" and "lab: secp256k1/tests passed in N s" per program. Mapped: all three to `signature-library`; `tests` and `noverify_tests` to `nonce-reuse` (src/tests.c's ECDSA edge cases check the default RFC 6979 nonce is deterministic and differs for 256 messages and 256 keys, `rfc6979_hmac_sha256_tests` checks its generator against known outputs, and src/modules/schnorrsig/tests_impl.h's `run_nonce_function_bip340_tests` that a bit flip in any input changes the BIP 340 nonce). Not mapped to `hash-functions`: its SHA-256 tests check the library's internal SHA-256 against known outputs, which says nothing about collisions or preimages, and Core hashes blocks and transactions with its own src/crypto.
- embargo (`pnpm brain embargo`, `brain/src/security/embargo.ts`, `cli.ts`): `var/embargo/<id>.json` (mode 600); `list`, `show`, `release`, `dismiss` (by hand; the owner's way is the admin, admin.md).
- disclosure gate (`core/src/disclosure.ts`, used by `brain/src/publish.ts` through `brain/src/security/gate.ts`): see SECURITY.md, T9. `disclosureContext` counts the ids of every advisory in `advisories.json` as public, beside the watch's latest 24.
- advisories and NVD (`pnpm brain advisories`, `brain/src/security/advisorylog.ts`, `nvd.ts`): merges the inbox's advisory feeds into `knowledge/security/advisories.json` (each page once, kept when the inbox loses it, newest first, at most 1000), asks NVD's CVE API 2.0 (`https://services.nvd.nist.gov/rest/json/cves/2.0?cveId=`, no key, one request every 6.5 s by `brain/src/http.ts`, a copy under six hours old reused from `var/cache/http/`) for the due CVE ids (`nvdDue`: never asked; a day after NVD lacked it; a week while NVD is still analyzing; else a month) up to `--nvd N` (default 8, `all` for every one), writes the file only when something changed, and prints every advisory with its threats and rule, then every threat-map CVE id with NVD's status, date, products and any finding, then the advisories' CVE ids NVD lacks. The advisories watch calls the same `refreshAdvisories` with 8 NVD reads each time it runs (every 6 hours) and commits `advisories.json` with `watches.json`; a failure there is printed and never fails the watch.

```sh
cat knowledge/runs/2026/<run id>.yaml; ls $SCRATCH/e2e/embargo
```

Proves it when the publisher prints "is embargoed for the owner", the run log's summary is "The notes of this run are withheld while the owner reviews part of it." with `read`, `open` and `injections` empty and only the harmless skipped statement in `rejected`, `git status knowledge/claims` is clean, and one `<id>.json` sits in the embargo dir. Remove the run log and restore `knowledge/review-queue.json` afterwards.

The lab, for real: `pnpm brain lab --jobs 3` for every maintained release, or `--version 31.3,30.5` for some (network for bitcoincore.org and git; the tests run under `heavy` on their own; downloads that still match are reused; about 370 MB under `var/security/lab/<version>/` per release). ## Gotchas

- The page is static: new watch readings or a lab run show after `pnpm bundle` and a deploy. The brain's hourly tick writes `knowledge/security/watches.json`; the weekly lab writes `lab.json` only for runs that passed or that the owner released from the embargo, so a failed run never appears here.
- Every sentence about a threat itself is a published claim. A threat whose claims are not yet published says "Being researched" in that section, never draft text.
- `page:/admin/security` (the owner's embargo queue) is covered by admin.md, not here.
- The owner maps advisories and settles NVD findings in `knowledge/security/advisory-map.yaml` (an `assign` entry, `exclude`, or `products` plus `expect` for a CVE that is rightly another project's), by hand or from the admin's "Advisories and NVD" page (`/admin/advisories`, admin.md), whose job edits the file in place; nothing else writes it. Keyword words belong there, never in a threat's `terms`: the disclosure gate reads terms as proof a finding is public.
- A matched advisory shows on its threat's page only after `pnpm bundle`; the dev server reads the new bundle on the next request.
