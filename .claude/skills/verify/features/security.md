# Security

A reader sees every known way Bitcoin can be attacked, by layer, with its live status, the published claims that explain and defend against each, the projects' advisories filed under each (with the rule that filed it), each threat's CVE ids checked against NVD, the watches' readings, the lab's run on the newest release of each maintained Bitcoin Core major (newest first) and on LND's newest release, and the newest advisories; an assistant reads the same through the `threats` and `watches` MCP tools. The Safety Desk shows the threats to a person who holds bitcoin by threat model, with their claims; `safety_desk` gives it to an assistant.

## Sub-features

- data: `bundle.security` (a `SecurityView` compiled by `core/src/security.ts` from `knowledge/security/threats/`, `watches.json`, `lab.json`, `advisories.json` and `advisory-map.yaml`), read through `web/lib/security.ts` (server-only: `security`, `allThreats`, `getThreat`, `watchById`, `claimsOf`, `securityScene`). The pure queries the MCP tools use are in `core/src/threatmap.ts` (`@blocklore/core/threatmap`).
- map (`/security`, `web/app/security/page.tsx`): the plain lede, counts in the header meta, a strip with one segment per threat in map order, the three statuses each with a one-line meaning, then every layer in `LAYERS` order with its counts and its threats. A threat row: status chip (a shape per status, so it reads without color: square defended, half watching, ring open), title linking to `/security/<id>`, published claim count (left out at zero), "being researched" when claims or mitigations are missing, watch count, lab tests ("lab N of M passing on K releases", counting a test as passing when it passed on every release that ran it, or "not run yet"), "raised by a watch".
- watches: one line per watch (title, a line of context from its data, value in its unit, a sparkline of its history, status chip); opening one shows what it measures, its documented thresholds (`WATCHES` in `core/src/watch.ts`), its source and when it was read. Empty state when `watches.json` has no readings.
- lab (BACKLOG 40): `bundle.security.labReleases` (`labReleases` in `core/src/security.ts`: of each of the newest `MAINTAINED_MAJORS` = 3 majors in `lab.json`, the run on its newest release, newest release first) then LND's newest run and LDK's (`LAB_LINES`: one line each), as a line per release (`LabReleases` in `web/components/security/parts.tsx`, the design system's `.lines`, so nothing scrolls sideways in the narrow column beside the scene): "Bitcoin Core 32.1" with a badge "50 of 50 tests passed", then when it ran, "Matched SHA256SUMS", "8 of 40 builder signatures good", "libsecp256k1's own tests: 3 of 3 programs passed" (only when the run has `secp256k1/` tests) and how long the tests took; an LND line reads "LND 0.21.8-beta" with "5 of 5 test packages passed", "Matched its signed manifest", "4 of 16 maintainer signatures good" and "Built from its source"; an LDK line reads "LDK 0.2.8" with "4 of 4 test modules passed", "Source is the commit its release tag names", "Tag signed by one of 6 listed maintainers" and "Built from its source"; below them the machine, "Bitcoin Core's tests 3 at a time, libsecp256k1's one by one, LND's packages one by one and LDK's modules one by one" and that an older release runs only the tests it has. The lede names libsecp256k1's test programs, LND's unit tests and LDK's tests. The header meta says "Lab: Bitcoin Core 32.1, 31.3 and 30.5, LND 0.21.8-beta and LDK 0.2.8" (`labReleaseList`). Empty state "The lab has not published a run yet". `labRuns` keeps every published run for progress and Nostr.
- advisories (BACKLOG 36, `core/src/advisories.ts`): `knowledge/security/advisories.json` (the brain's: every advisory the watch has read, with the CVE and GHSA ids it names, and NVD records) is matched to threats at bundle time by `matchAdvisory` under the owner's `knowledge/security/advisory-map.yaml`, one rule per match, strongest first: `owner` (the map's `assign`; an empty list means on no threat), `record` (the threat's history cites its page), `claim` (a published claim the threat lists, in either list, cites its page as a source or names one of its CVE or GHSA ids in its statement or a source's title; `threatCites`, passed the store's published claims by `securityView`, `brain advisories` and the admin's view; the threat page says "Filed here because a published claim this threat lists cites it:" with each claim linked), `id` (a CVE or GHSA id the threat's history or terms list), `source` (the map's `sources` files every advisory of a project), `term` (one of the threat's terms in the title), `keyword` (the map's `keywords` in the title); `exclude` takes a threat away. Words match whole, any case (`hasWords`). `/security` shows the 8 newest (title linked, source, date, severity, each CVE id linked to NVD with "in NVD since" or "Not in NVD yet", and "Filed under" its threats or "On no threat yet: an advisory to map"), with "N read, M filed under a threat, K to map" beside the heading. An advisory nothing files and the map does not name is `bundle.security.advisories.unmatched` and `bundle.gaps.advisories` (gaps.md), and rides into the research task of the topic its project's filed advisories are mostly on (`advisoryTopics`), else the topic nearest its title and its page's path words, as `<advisory url="...">title</advisory>` escaped and labeled as data, asking for claims that cite its page, named under the threat they explain (`threats` in run.yaml), so the `claim` rule files it once they are published and linked.
- NVD (BACKLOG 38): every CVE id a threat's history or terms name is a `CveCheck` (`checkCve`): `missing` (NVD has no record), `rejected`, `product` (NVD's CPE pairs, CNA data and description name no project the check expects: the map's `expect`, else the projects of advisories that carry it, else the project of the page the history cites it at by the map's `products[].pages`, else any project in `products`), `unnamed` (NVD names nothing the map knows), or none. Findings never change knowledge text.
- report: the rail lists each project's private security contact and policy from `DISCLOSURE` (`core/src/disclosure.ts`).
- threat (`/security/<id>`, `web/app/security/[threat]/page.tsx`): statically generated for every threat, `dynamicParams = false` (an unknown id is 404). Crumbs to the map and the layer, status chip and meaning, which watch raised it when `raisedBy` is set; "What it is" and "What defends against it" as `ClaimLine`s linking `/claims/<id>` (only published claims), each saying "Being researched" and that it is on the brain's research list when it has no published claim (`missing`); its watches with value, context, a wider sparkline, measures, thresholds, source and last read; its lab tests by release (`LabMatrix`: a table per project the threat's tests belong to (`labTestProject`), captioned "Bitcoin Core" or "LND", each the design system's `.table` in a keyboard-scrollable `TableWrap` named "This threat's LND tests by release" and so on, a row per test ("Package" for LND), a column per release of that project in `labReleases` with its date, each cell Passed, Failed or Not run when that release's run did not have the test, e.g. `p2p_private_broadcast.py` on 30.5; Not run yet when the lab has no run; a row's label is `labTestLabel` in `core/src/security.ts`: the release check in words, `secp256k1/tests` as "libsecp256k1 tests", `lnd/watchtower/lookout` as "LND watchtower/lookout" (old-state has only LND rows, pinning both tables, lightning-bugs LND's five), with a sentence under the heading saying what the libsecp256k1 rows are when the threat has them, as `signature-library` and `nonce-reuse` do); "Its advisories" (`#advisories`, shown when it has any or lists the advisories watch): each advisory with source, date, severity, CVE ids against NVD, and the sentence of the rule that filed it ("Filed here because this threat's public record cites its page.", "...record names CVE-...", "...with every advisory LND publishes...", or "Matched by words in its title: <q>memory DoS</q>, ..." for a term or keyword); "Checked against NVD" (`#nvd`, when its record names CVE ids): a callout "N findings for the owner: ids" and per id a badge (Matches, Not checked yet, No NVD record, Rejected by NVD, Another product, Product unclear), "In NVD since", what NVD says it affects (vendor:product), the projects it names, where the threat names it, when checked, and "For the owner: ..." per finding; its public record (`history` refs linked, host and date, and a CVE ref's NVD date or "see the NVD check"); the rail links its topic and its layer.
- desk (BACKLOG 23, `/safety`, `web/app/safety/page.tsx`, the Security view's second tab in `web/lib/nav.ts`): `DESK` in `core/src/desk.ts` (`@blocklore/core/desk`) names the threat models in order (what-you-hold, who-knows, where-you-are, scams) and each one's threat ids; `deskView(bundle.security)` gives each model's `ThreatView`s and counts (threats, explained, claims). The page: header meta "12 threats", "N of 12 explained", "M published claims"; a callout that Blocklore never asks for a seed, key, xpub or address and what the evaluator requires of a safety claim; per model its title and question, then per threat its title (an h3 linking `/security/<id>`), "being researched: ..." naming the missing parts, and "What it is" and "What defends against it" as `ClaimLine`s numbered down the page. No status chips: "open" reads as alarm on a person's threat. `core/test/desk.test.ts` checks every desk id is on the real map once and every `people` threat is on the desk. Check: `curl -s localhost:3721/safety` has the four model headings and "Mistyped addresses that a checksum fails to catch" with its two claims; axe on `/safety`.
- scene: `securityScene()` in `web/lib/security.ts` gives `SceneData["security"]` (layers, threats with live status) for the scene's security layer.
- links (BACKLOG 42): a threat's `claims` and `mitigations` change from the admin's Threat map page (`threat.link`, `threat.unlink`; see admin.md, "threat map"), where code suggests published claims that name the threat and the owner links them, and from research: run.yaml `threats` (`{threat, explains, defends}`, `RunNotes` in `brain/src/staging.ts`, asked for in the task's threats section by `researchTask`), checked by `threatErrors` in `brain/src/research.ts` (a threat on the map; claims in the run or published whose statement names the threat by `threatPhrases` and `namesPhrase`), kept by publish (`runLinks`, `recordLinks`) in the private `var/security/links.json` (`BLOCKLORE_SECURITY_DIR` moves it), and linked by the hourly step "threat links". Published claims that name a gap threat but are not linked go with it in the gap map (`named` on each `TopicGap` threat, `threatSuggestions` capped at `NAMED_MAX` 8 in `core/src/bundle.ts`) and into the task under the threat ("published, names it: <id>: <statement>"), for research to name under `explains` or `defends` or leave out; the threat links are then (`linkResearch`: `researchLinks` in `core/src/threatadmin.ts` decides link, wait while the claim is in `var/review`, or drop with why; each edit goes through `editThreat`, `formatYaml` (`brain/src/format.ts`) and `checkThreat` as the owner's does; one owner commit; `knowledge/security/threats` is urgent for the ship, so it deploys at once). The brain edits that one list of that one file. A link closes the threat's gap on `/gaps` and in the research task once the site rebuilds. `core/test/threatadmin.test.ts` covers the matching, the view and the refusals; `brain/test/threatlinks.test.ts` the edit, the gap closing in the view and the bundle, and the job's checks, in a copy of the store; `researchLinks` (link, wait, drop and why) in `core/test/threatadmin.test.ts`, and research's hourly step in `brain/test/threatlinks.test.ts` (one linked as lint formats it, two dropped with why, nothing left waiting, a second run does nothing).
- mcp: `safety_desk` (`model` optional: the desk as `/safety` shows it, each threat with `being_researched` and its claims in brief), `threats` (`id`, `layer`, `status`, all optional) and `watches` (`id` optional) in `web/lib/mcp.ts`; see mcp.md for the driver. `watches` carries `lab` (`labReport` in `core/src/threatmap.ts`: each maintained Core release's run, newest first, then LND's and LDK's, with its project, when, platform, verified, jobs, seconds, passed of run and each test's result). A threat in the list carries `lab` (`labCounts`: tests, run, passed, and passed of run per release); one threat carries `lab` (`threatLab`: each test with its `project` and the `releases` of that project, ok null where that release's run did not have it). The list carries `advisories` per threat and `nvd_findings`, and a top-level `advisories` summary (`advisorySummary`: counts and `to_map`); one threat carries `advisories` (`threatAdvisories`: each with `filed_by {rule, matched, by_words}` and its NVD states) and `nvd` (`cveCheck`: state, status, published, affects, names, expected, finding, mismatch).

## The brain's side: watches, lab, embargo

- watches (`pnpm brain watch`, `brain/src/security/watches.ts`; readings and thresholds in `core/src/watch.ts`): each due watch (or all with `--force`, one with `--only <id>`) reads public data through `brain/src/http.ts`, stamps a reading into `knowledge/security/watches.json` (status ok, elevated, alert or unknown; a short history) and logs a `watch` event per status change to the public feed log `var/control/feed.jsonl` (through `logEvent` in `brain/src/security/events.ts`; the daemon sends it to the site, the front page shows it as "Watching"). Blocks come from mempool.space and blockstream.info, which must agree on every id, time, target and version, read side by side in pages aligned to each one's size; `var/security/blocks.json` follows the last 160 blocks for reorgs and keeps each version of the tip's difficulty period and the one before, for the version bits (`brain/src/signaling.ts`, see [proposals](proposals.md)), whose `knowledge/chain/signaling.json` rides in the same commit. The hourly tick runs `watch({ force: false, commit: true })`.
- lab (`pnpm brain lab [--version 31.3,0.21.8-beta,ldk:0.2.8] [--project core|lnd|ldk]`, `brain/src/security/lab.ts`): the newest point release of each maintained Core major, then LND's newest, then LDK's (`--project lnd` for LND alone, `--project ldk` for LDK; `splitVersions` tells a named Core release from an LND one by its form, and takes `core:`, `lnd:` or `ldk:` before a version, which LDK's needs since `0.2.8` reads as Core's) (`maintainedReleases` over `git ls-remote --tags`; a major with only rc tags is not out), or the versions named, one after another; for each, `SHA256SUMS` and builder signatures checked, that release's functional tests mapped to threats (only those it has; the rest printed as left out) run in regtest against its binaries (`-j` modest) under `heavy`, then libsecp256k1's own test programs the map names (`secp256k1/tests`, `secp256k1/noverify_tests`, `secp256k1/exhaustive_tests`; `selectTests` keeps them apart from the scripts) built from that release's `src/secp256k1` and run (below), then the disclosure gate on that release alone. A passing run joins `knowledge/security/lab.json` beside the other releases' runs (`keepLabRuns`: newest first, up to 12 of each major); a failure or a release that did not verify is embargoed and nothing public changes for it. A release that cannot run does not stop the others; the lab fails at the end naming it. It ends with one line per release: result, passed of run, the tests' seconds and the whole run's. One commit for everything published. The weekly tick runs `lab({ publish: true, commit: true })`. Releases before 32.0 write `config.ini.in` components as `@X_TRUE@` line prefixes (`configIni` fills both forms; left unfilled, the runner printed "No functional tests to run" and every test was held as failed). The runner gets `TEST_RUNNER_PORT_MIN` from `portBase`: the first base from 11000 in steps of 1000 whose p2p, RPC (+5000) and proxy (+10000) windows nothing on the machine listens on (`listeningPorts` reads `/proc/net/tcp` and `tcp6`), printed as "lab: test ports from N"; with the framework's default 11000 another project's server on 11600 failed one test per release on 2026-11-23.
- LND (`brain/src/security/lnd.ts`, BACKLOG 40): `newestLndRelease` over `git ls-remote --tags` of lightningnetwork/lnd (`vX.Y.Z-beta`, never an rc, never another module's tag). The trusted side first: a sparse, depth 1, blobless clone of LND at the tag holding only `scripts/keys/` and `scripts/verify-install.sh` (`<lab>/lnd/<v>/keys/`, its commit printed); `lndSigners` reads its `KEYS+=(...)` (16 on 0.21.8-beta) and `MIN_REQUIRED_SIGNATURES` (5). Then the release's files into `<lab>/lnd/<v>/dl/`: the manifest, each maintainer's `manifest-<user>-v<v>.sig` that exists, and `lnd-source-v<v>.tar.gz` (kept while `manifestMatch` still holds). Each signature is checked with `gpg --status-fd 1 --verify` against a keyring of its own holding only that user's key at its fingerprint (`<lab>/lnd/<v>/gnupg/`); `signatureState` reads gpg's exit and status: GOODSIG good, EXPKEYSIG expired (gpg still says "Good signature"; LND's script counts it, the published count does not), anything else bad. `lndVerified`: the tarball matches, nothing bad, at least one good, good and expired together at least the minimum. Only then the source is extracted (`<lab>/lnd/<v>/src/`), `goVersionFromMod` reads go.mod (`go 1.26.10` on 0.21.8-beta), `goArchive` picks the archive and SHA-256 from `https://go.dev/dl/?mode=json&include=all`, and the toolchain is unpacked at `<lab>/go/go1.26.10/go` with a `.sha256` stamp, reused while the stamp matches. `goEnv` puts GOROOT, GOPATH, GOMODCACHE, GOCACHE, HOME, XDG dirs and TMPDIR under the lab, sets `GOTOOLCHAIN=local`, `GOFLAGS=-mod=readonly`, `GOENV=off` and drops every `GO*` variable the caller had; `go list -deps -test` fetches the modules (online), and each `go test -json -count=1 -timeout=20m -p=<jobs> -tags="<unitTags>" ./<pkg>` runs offline (`GOPROXY=off`) under `heavy /usr/bin/time ... timeout` (45 min a step), its output in `<lab>/lnd/<v>/runs/<at>.<pkg>.jsonl`; `parseGoTest` takes the package's own verdict and `Elapsed`, the failing tests and their output. `selectLndPackages` takes the map's `lnd/` names (`LND_PACKAGES`: contractcourt, htlcswitch, lnwallet, sweep, watchtower/lookout). A failing package or a release that did not verify is held with LND's contact alone (`projects` on `hold`, `disclosureContacts`). Mapped (the header of `lnd.ts` cites file and function): `old-state` contractcourt, lnwallet, watchtower/lookout; `pinning` contractcourt (`blocksPassedSplitPublish`, `TestBreachDelayedJusticeConfirmation`); `lightning-bugs` all five. Left unmapped: `channel-jamming` (its only LND measure is tested by an integration test that needs bitcoind) and `replacement-cycling` (no unit test gives a resolver a mempool).
- LDK (`brain/src/security/ldk.ts`, BACKLOG 40): `newestLdkRelease` over `git ls-remote --tags` of lightningdevkit/rust-lightning (`vX.Y` or `vX.Y.Z`, never an rc or beta), `previousLdkRelease` the final before it. LDK has no release files (GitHub lists no assets), so the signed annotated tag is what is checked. A fresh depth 1 clone at the tag (`<lab>/ldk/<v>/src/`) and a fetch of the previous tag; `ldkMaintainers` reads SECURITY.md's ` * <40 hex> (Name)` lines at both (6 at v0.2.8 and v0.2.7) and `countedMaintainers` keeps a key only when both list it. Each counted key comes from `https://keys.openpgp.org/vks/v1/by-fingerprint/<fpr>` into its own keyring (`<lab>/ldk/<v>/keys/`) and only that fingerprint is exported into `<lab>/ldk/<v>/gnupg/`. `git cat-file tag v<v>` gives the tag object; `splitSignedTag` cuts it into the signed payload and the signature (`tag.payload`, `tag.sig`), gpg `--status-fd 1 --verify` checks them, and `tagSigner` takes GOODSIG with VALIDSIG naming a counted primary key (the signature itself is by a subkey; `signatureState` as LND's). `ldkVerified`: the tag names itself and the commit at HEAD, `git status --porcelain` is empty, and the signer is good. Only then: `rustStable` reads `https://static.rust-lang.org/dist/channel-rust-stable.toml` for rustc, cargo and rust-std for this machine (`rustTriple`), each `.tar.xz` checked against its `.sha256` and the manifest's `xz_hash`, unpacked and merged at `<lab>/rust/<version>/` with a stamp, reused while intact. `cargoEnv` puts CARGO_HOME (`<lab>/rust/cargo-home`), CARGO_TARGET_DIR (`<lab>/ldk/<v>/target`), HOME, XDG dirs and TMPDIR under the lab and drops every CARGO and RUST variable the caller had. LDK commits no Cargo.lock: the first run resolves one (`cargo generate-lockfile`) and keeps it at `<lab>/ldk/<v>/Cargo.lock`, later runs copy it in; `cargo fetch --locked` (online) then `cargo test -p lightning --lib --locked --offline -j<jobs> --no-run` builds (60 min limit) and each module runs `cargoTestArgv` (`<module>::` filter, `--test-threads=<jobs>`, 45 min limit) under `heavy /usr/bin/time ... timeout`, its output in `<lab>/ldk/<v>/runs/<at>.<module with / as _>.log` (`<at>.build.log` for the build); `parseLibtest` reads libtest's `test result:` line and the failures. A module with zero tests is missing, not passed. `selectLdkModules` takes the map's `ldk/` names (`LDK_MODULES`: chain/package, ln/functional_tests, ln/monitor_tests, ln/onion_route_tests). A failing module or a tag that did not verify is held with LDK's contact alone (security@lightningdevkit.org). Mapped (the header of `ldk.ts` names each test): `old-state` ln/functional_tests, ln/monitor_tests; `pinning` chain/package, ln/monitor_tests; `lightning-bugs` all four. Left unmapped: `channel-jamming` (the crate has no endorsement or accountability signal to test) and `replacement-cycling` (LDK sees only blocks and confirmed transactions, and no test puts its fee bumping under a cycling attack).
- libsecp256k1 (`brain/src/security/secp256k1.ts`, BACKLOG 40): the source tarball is in the release's `SHA256SUMS`, so its `src/secp256k1` is the verified copy the release's binaries were built from. No cmake on the box: `secpBuild` reads the release's `cmake/secp256k1.cmake` (Core's forced modules: ECDH off, recovery and musig on; RelWithDebInfo; hidden visibility), `src/secp256k1/CMakeLists.txt` (module defaults, `ECMULT_WINDOW_SIZE`, the comb for `ECMULT_GEN_KB`, `USE_ASM_X86_64` on x86_64, `-std=c90`, `-O2 -g`) and `src/secp256k1/src/CMakeLists.txt` (module blocks in order with their dependencies, the precomputed tables, each program's source and defines: `VERIFY`, `SUPPORTS_CONCURRENCY=1` from 31.3; 32.1's `add_executable_and_tests` function expanded), and throws on anything it cannot read the same way, which fails the programs like a test. `secpCommands` gives the gcc calls: the precomputed tables as objects, then each program from `tests.c` or `tests_exhaustive.c`. Each gcc call and each program runs as `heavy /usr/bin/time -f %e -o <file> timeout ...` (15 min per build step, 60 min per program, the seconds counted only once it holds a slot) in `<lab>/<v>/secp256k1/`, with no arguments (16 iterations; exhaustive 2). `secpPassed`: exit 0 and the program's own last line ("no problems found", or the unit test framework's "Total execution time: N seconds" from 31.x). Each program is a `LabTest` (`secp256k1/<program>`, its result, its seconds) in that release's run; the run's seconds add them; the private record keeps the gcc commands, build seconds, modules and each program's last 40 lines (with its random seed), and a failed program's lines join the tail the admin shows. A failure or a build error holds the release like any failed test, and the embargo names `secp256k1-security@bitcoincore.org` beside Core's address. The lab prints "lab: libsecp256k1 0.8.1 from Bitcoin Core's src/secp256k1, modules ...", "lab: libsecp256k1 built in N s" and "lab: secp256k1/tests passed in N s" per program. Mapped: all three to `signature-library`; `tests` and `noverify_tests` to `nonce-reuse` (src/tests.c's ECDSA edge cases check the default RFC 6979 nonce is deterministic and differs for 256 messages and 256 keys, `rfc6979_hmac_sha256_tests` checks its generator against known outputs, and src/modules/schnorrsig/tests_impl.h's `run_nonce_function_bip340_tests` that a bit flip in any input changes the BIP 340 nonce). Not mapped to `hash-functions`: its SHA-256 tests check the library's internal SHA-256 against known outputs, which says nothing about collisions or preimages, and Core hashes blocks and transactions with its own src/crypto.
- embargo (`pnpm brain embargo`, `brain/src/security/embargo.ts`, `cli.ts`): `var/embargo/<id>.json` (mode 600); `list`, `show`, `release`, `dismiss` (by hand; the owner's way is the admin, admin.md).
- disclosure gate (`core/src/disclosure.ts`, used by `brain/src/publish.ts` through `brain/src/security/gate.ts`): see SECURITY.md, T9. `disclosureContext` counts the ids of every advisory in `advisories.json` as public, beside the watch's latest 24. Disclosure sources (`isDisclosureSource`): Core's advisories page and its `disclose-` or `disclose_` posts, bitcoin.org's `/en/alert/` pages, Optech's responsible-disclosures topic, GitHub advisories, NVD's detail page and its CVE API record (`services.nvd.nist.gov/rest/json/cves/2.0?cveId=`), cve.org, MITRE and the wiki's CVE list.
- lifting (`liftHolds` in `brain/src/security/gate.ts`, the hourly `disclosure` tick step after `watch`): every held research candidate the rule passes against the store as it is now goes to `var/review/` with the single reason `LIFTED` (never `RELEASED`, so `screenEmbargo` screens it again each time), and the hold is closed in `closed.jsonl` as `lifted`. A draft whose id already waits, or that published since (not an update), is closed without being queued. Lab items are never lifted. The step's loop note is empty on purpose.
- advisories and NVD (`pnpm brain advisories`, `brain/src/security/advisorylog.ts`, `nvd.ts`): merges the inbox's advisory feeds into `knowledge/security/advisories.json` (each page once, kept when the inbox loses it, newest first, at most 1000), asks NVD's CVE API 2.0 (`https://services.nvd.nist.gov/rest/json/cves/2.0?cveId=`, no key, one request every 6.5 s by `brain/src/http.ts`, a copy under six hours old reused from `var/cache/http/`) for the due CVE ids (`nvdDue`: never asked; a day after NVD lacked it; a week while NVD is still analyzing; else a month) up to `--nvd N` (default 8, `all` for every one), writes the file only when something changed, and prints every advisory with its threats and rule, then every threat-map CVE id with NVD's status, date, products and any finding, then the advisories' CVE ids NVD lacks. The advisories watch calls the same `refreshAdvisories` with 8 NVD reads each time it runs (every 6 hours) and commits `advisories.json` with `watches.json`; a failure there is printed and never fails the watch.

## Gotchas

- The page is static: new watch readings or a lab run show after `pnpm bundle` and a deploy. The brain's hourly tick writes `knowledge/security/watches.json`; the weekly lab writes `lab.json` only for runs that passed or that the owner released from the embargo, so a failed run never appears here.
- Every sentence about a threat itself is a published claim. A threat whose claims are not yet published says "Being researched" in that section, never draft text.
- A threat may still list a claim the owner withdrew (the build stays green), but a withdrawn claim no longer explains it: the threat's page, the map and the gap map treat that part as missing again until another claim is linked (`core/test/security.test.ts`, "a claim the owner withdrew").
- `page:/admin/security` (the owner's embargo queue) is covered by admin.md, not here.
- The owner maps advisories and settles NVD findings in `knowledge/security/advisory-map.yaml` (an `assign` entry, `exclude`, or `products` plus `expect` for a CVE that is rightly another project's), by hand or from the admin's "Advisories and NVD" page (`/admin/advisories`, admin.md), whose job edits the file in place; nothing else writes it. Keyword words belong there, never in a threat's `terms`: the disclosure gate reads terms as proof a finding is public.
- A matched advisory shows on its threat's page only after `pnpm bundle`; the dev server reads the new bundle on the next request.
