# Admin

The owner's console at `/admin`: email sign-in, the evaluator, research control with a live feed, runs and usage, the agenda, the gate policy, the threat map's links, lessons and focus, triage of reader suggestions, and settings (ADMIN.md).

## Sub-features

- sign-in (`web/lib/admin/auth.ts`): only `OWNER_EMAIL` gets a link. `POST /api/admin/login {email}` answers `{ok:true}` whatever the address (5 links an hour per visitor, 10 in all) and mails `/admin/auth#t=<token>` from `login@blocklore.space` through Resend (`RESEND_API_KEY`); without that key, `next dev` prints the link to its log. The token is in the fragment, so no server log sees it. `/admin/auth` shows a "Sign in" button that POSTs `{t}` to `/api/admin/auth` (mail scanners that open links cannot use it up); the token works once (Redis `getdel`) for 15 minutes. The session id goes in an `HttpOnly`, `SameSite=Lax` cookie (`__Host-bl_admin` in production, `bl_admin` in dev); Redis keeps only its SHA-256 for 30 days. Sign out ends it; "Sign out everywhere" (Settings) ends them all.
- devbox link (`web/app/api/control/link/route.ts`, `pnpm brain admin-link`): a request signed under `CONTROL_KEY`, fresh and with an unused nonce, gets the same kind of link; anything else 401.
- guard: every page under `app/admin/(console)/` runs `requireOwner()` in its layout (307 to `/admin/login`); every `/api/admin/*` route runs `ownerFor(req)`: a session, and for POSTs an `Origin` that is the site's own (outside production also `http://localhost:<any port>`, so each session's dev site works; a sign-in link for any other origin goes to the canonical site) and `Sec-Fetch-Site` same-origin (403 or 401 otherwise). `robots.txt` disallows `/admin`, `/api/admin/` and `/api/control/`; the pages set `noindex`.
- commands (`web/lib/admin/control.ts`, `POST /api/admin/command {cmd}`): the body must parse as `Command` (`core/src/control.ts`); a review decision whose ids or hashes no longer match the queue the daemon last sent is refused with 409 before signing, and so is a `claim.revoke` whose hash is neither the deployed claim's nor one the evaluator's view lists as just published. The site signs the envelope under `CONTROL_KEY` with the owner's address and pushes it to `ctl:cmd`.
- poll (`GET /api/admin/poll[?live=1][&results=id,...]`): the daemon's last state (online when it synced in the last 75 s), the live session events and the results of the page's commands; sets `ctl:watch` so the daemon syncs every 3 s. Pages poll it every 3 s while visible (`useBrain` in `web/components/admin/live.tsx`) and show each sent command's progress (Sent, Received, Running, Done or Failed).
- security embargo (`/admin/security`, `web/components/admin/Embargo.tsx`): the findings the disclosure gate keeps private (SECURITY.md, T9), which the daemon sends as `embargo` on its sync (`EmbargoView` in `core/src/control.ts`, built by `embargoView` in `brain/src/security/embargo.ts`) and the site keeps in `ctl:embargo`. Each shows the finding, why it was held, and each project's private reporting address and policy. "Release" stays off until the owner ticks "The project has published an advisory or a fix"; Release and Dismiss send `embargo.decide`, which the command route refuses with 409 when the id left the embargo, and which runs as a job (`settle` in `brain/src/security/cli.ts`: a released lab run is committed and shipped, a released research candidate joins the review queue).
- advisories and NVD (`/admin/advisories`, `web/components/admin/AdvisoryMap.tsx`; the nav's "Advisories and NVD" under "Security embargo"): the daemon builds `AdvisoryAdminView` (`core/src/advisoryadmin.ts`) from its checkout with `advisoryView` (`brain/src/security/advisorymap.ts`) whenever HEAD or the map's or the advisories' file changes, and sends it as `advisories` on its sync; the site keeps it in `ctl:advisories` and writes it before the sync's results. Four sections: "Advisories to map" (each advisory no rule files: "File under threats" opens the 40 threats by title, grouped by layer, as checkboxes; "File under N threats" or "It concerns no threat" sends `advisory.assign` keyed by its first CVE id, else GHSA id, else page), "NVD findings" (each `CveCheck` with a finding: for "Another product", a name prefilled from NVD's first vendor:product pair and the pairs to claim, "Record it as expected" sends `advisory.expect`; "Expect <project>" when NVD names a project the map has; "No NVD record", "Rejected by NVD" and "Product unclear" say why they stay open), "Your placements" and "Settled by you" (each with Undo: `advisory.unassign`, `advisory.unexpect`). A row whose command is open says "Sent: the brain commits it as yours" until the result is done or failed; on done the page refreshes from `ctl:advisories`. The command route refuses (409) a command `advisoryCommandProblem` finds does not fit the map the daemon last sent; the job checks it again, edits the file as a YAML document, formats it (`formatYaml`), checks it (`checkAdvisoryMap`: schema, threat map, no dash, says what was asked), writes, commits as the owner and ships (`brain/src/jobs.ts`).
- gate policy (`/admin/policy`, `web/components/admin/GatePolicy.tsx`; the nav's "Gate policy" under "Direct the brain", after Agenda): the daemon builds `GatePolicyView` (`core/src/gatepolicy.ts`) from its checkout with `policyView` (`brain/src/policy.ts`) whenever HEAD, `brain/policy/topics.yaml`, `brain/agenda/seed.yaml` or the review queue changes, and sends it as `policy` on its sync; the site keeps it in `ctl:policy` and writes it before the sync's results. The lede says what the two flags do (contested holds every claim on the topic for the evaluator's closer checks; safety advice also needs two independent sources), that an unlisted topic counts as contested, that loosening the gate is the owner's decision and that claims already waiting keep waiting. "Topics" lists every agenda topic in the agenda's order, then published ones it lacks, then any the file lists that are neither (shown, not changed): each row (`li[data-slug]`) says whether it is on the agenda and published, how many claims whose first topic it is wait (`[data-waiting]`, the daemon's queue), and the file's flags ("The file sets it as ...") or "Not listed: every claim on it waits for the evaluator"; then two Yes/No groups, "Contested" and "Safety advice" (`fieldset`s of the `segmented` control, `aria-pressed`), and Save. A listed topic starts with the file's flags pressed; an unlisted one with nothing pressed, and Save stays off ("Pick both flags to save.") until both are picked; Save is off while the picks equal the file, and plain until there is a change to save. Save sends `policy.topic`; the row says "Sent: the brain commits it as yours" until the result is done or failed, and on done the page refreshes from `ctl:policy`. "Contested terms" lists the file's terms in order (`li[data-term]`); the cross asks "Remove" or "Keep", and Remove sends `policy.term` with `add: false`; "Add a term" checks the term as the command does (`termProblem`: no secret, 1 to 40 characters on one line, a letter or digit, no refused dash; not already listed in any case) and sends `policy.term` with `add: true`, the new term showing "Sent" until it is done. The command route refuses (409) what `policyCommandProblem` finds does not fit the view the daemon last sent; the job checks it again, edits the file as a YAML document, formats it (`formatYaml`), checks it (`checkPolicy`: parses as the policy, holds exactly what the command asked, differs only in the lines of the entry it names), writes, commits as the owner and ships (`brain/src/jobs.ts`). Developers and assistants never change the gate policy: drive the page only against a scratch daemon.
- threat map (`/admin/threats`, `web/components/admin/ThreatMap.tsx`; the nav's "Threat map" under "Direct the brain", after Debate maps): the daemon builds `ThreatAdminView` (`core/src/threatadmin.ts`) from its checkout with `threatView` (`brain/src/security/threatlinks.ts`) whenever HEAD or a file in `knowledge/security/threats/` changes, and sends it as `threats` on its sync; the site keeps it in `ctl:threats` and writes it before the sync's results. The header counts the threats with a gap and the suggestions. A section per layer in the map's order (`section[aria-labelledby=layer-<id>]`), each threat a row (`li[data-threat]`, `data-gap` naming the lists with no published claim) with the gaps first, then by id: its title linking its public page, its id, status and topic, a "Needs ..." badge per missing list; "What it is" and "What defends against it" (`[data-part=claims]`, `[data-part=mitigations]`), each claim (`[data-linked]`) with its statement, its id linking `/claims/<id>`, "Withdrawn" when it was, and Unlink, which asks "Unlink" or "Keep" and sends `threat.unlink`; "Code's suggestions" (`[data-suggestion]`, at most 12): published claims it does not list whose statement names one of its terms or its id's words (`namesPhrase`: whole words in order, any case, spaces or hyphens between, an optional plural), on its topic first, each saying which phrase it names and whether it is filed under another topic, with "Link as what it is" and "Link as a defense" (`threat.link`); and "Link another published claim" (an id field over a datalist of every published claim, a choice of list, Link off until the id is a published claim the threat does not list, as `threatCommandProblem` says). A claim sits in at most one of a threat's lists. The command route refuses (409) what `threatCommandProblem` finds does not fit the view the daemon last sent; the job checks it again, edits that one threat's file as a YAML document, formats it, checks it (`checkThreat`: parses as a threat, is the threat before with the command applied, no refused dash, differs only in the line of the list it names), writes, commits as the owner and ships. Code suggests and never links: drive the page only against a scratch daemon.
- weekly review (`/admin/loop`, `web/components/admin/LoopReview.tsx`; the nav's "Weekly review" under "Runs and usage"): the latest `LoopReview` (`core/src/loopreview.ts`), which the daemon reads from the newest `var/loop/reviews/<week>.json` (`latestLoopReview` in `brain/src/loopreview.ts`) whenever a review is written and sends as `loop` on its sync; the site keeps it in `ctl:loop` (`LoopReviewView` in `core/src/control.ts` refuses a review whose proposal is not a `Command`). The header says the week and when it was compiled; "Findings (N)" lists each finding (`article[data-code]`) most weight first: a title, `findingText`, its evidence as links to the page that shows each kind (session to Runs, batch and decision to the Evaluator's decisions, topic to the Agenda, a published claim to `/claims/<id>`, a waiting claim to the Evaluator, a report to Reader reports, a source to its URL), and its proposal as a button with the proposal's label that sends the command through `useBrain().send` (the sent list above the findings follows it; the finding says "Sent: waiting for the brain" until the result is done or failed). A proposal that already holds under the daemon's current settings (`proposalDone`: the lesson is kept, the setting already has that value) shows "Done" and no button; a finding no command fits says so. Then "The week in numbers", "Claims by topic" and "Rules the evaluator held claims back on". The Overview shows one line (`p[data-loop-findings]`) with the count and the first finding, linking here, while the latest review has findings. Nothing on the page is sent until the owner presses a button.
- pages: Overview (status, the weekly review's line when it has findings, gated claims waiting, the Claude subscription (connected, at its limit, or not connected) with sessions and minutes today, sessions today, devbox head versus the live build, next session, start, pause, deploy, the ticks with "Run now", recent sessions, results); Evaluator (`/admin/evaluator`, from `ctl:evaluator`: who decides, the evaluator or "Hold for me", which shows the old queue of held claims by topic to approve with a note or reject with a reason and "Teach research this"; the state, backlog, last batch and who signed its decisions; "Evaluate now"; the threshold, window, batch size and test claims per batch; the catch rate lately and in all, by kind; withdraw a published claim by its row or by id, with a reason; recent decisions with every check's result; `/admin/review` redirects here); Research (start on a topic or the planner's pick with a focus, stop, the live feed, mode off/daily/continuous, hour, count, rest, model, most minutes and most turns a session, skip topics in review); "Your Claude subscription" first on Research (Not connected, At its limit or Connected; paste a `claude setup-token` token, which `POST /api/admin/subscription` seals under `CONTROL_KEY` (`core/src/node/seal.ts`) into a `subscription.connect` command; the daemon's job (`brain/src/subscription.ts`) opens it, checks it with a one-turn haiku session and writes `.env` at mode 600, then the daemon sets it in its own environment; optionally turn research to continuous; Replace the token; Disconnect sends `subscription.disconnect`); Runs and usage (the subscription, sessions and minutes over 7 days, use of your plan by day); Agenda (topics by need, research now, edit scope, add, remove when empty); Debate maps (`/admin/debates`: each published map with its positions and claim count and a Withdraw button that asks for a reason and sends `debate.withdraw`, which the command route refuses with 409 for a map the site does not show; withdrawn maps below with the reason; never press Withdraw on a real map, it is the owner's veto, so prove the brain side with `brain/test/debates.test.ts` and the page with `tools/admin-check.ts`, which screenshots it); Threat map (`/admin/threats`: see "threat map" below; never press Link or Unlink against the real brain, drive it with `threatadmincheck.ts` against a scratch daemon); Lessons and focus; Reader suggestions (`/admin/questions`: every status, including waiting and declined, triage to researching, answered or declined, public note, answering claims, and for a waiting or accepted question its nearest topic and the published runs that carried it (queue.md); `POST /api/admin/queue` runs `updateProblem` (the brain's rules: published claims, a styled, secret-free note) and then writes Redis through `updateQueue`, and a suggestion is public only once triaged here or by the brain, queue.md); Reader reports (`/admin/reports`: every report with its private notes and outcome, "Dismiss as abuse", "Restore and recheck", "Recheck again"; `POST /api/admin/reports`, problems.md); Signing (`/admin/signing`, [orangecheck](orangecheck.md)); Settings (pause, ticks on or off, ping, deploy, "Post to Nostr" with the preview of the next notes ([nostr](nostr.md)), sign out everywhere). There is no Ask switch or budget: the site runs no model for readers.

## How to reach it

- Dev: `web/.env.development.local` (gitignored, mode 600) holds a throwaway `OWNER_EMAIL=owner@example.test`, `CONTROL_KEY` and `BRAIN_SYNC_TOKEN`; `next dev` reloads it without a restart. Make one with `node -e 'const r=()=>require("crypto").randomBytes(32).toString("hex");require("fs").writeFileSync("web/.env.development.local",`OWNER_EMAIL=owner@example.test\nCONTROL_KEY=${r()}\nBRAIN_SYNC_TOKEN=${r()}\n`,{mode:0o600})'`. Without Redis, dev keeps sessions, commands and state in memory.
- A daemon for the dev site, with its own state so nothing touches `var/control/` (run in the background): `set -a; . <(grep -E '^(CONTROL_KEY|BRAIN_SYNC_TOKEN)=' web/.env.development.local); set +a; BLOCKLORE_CONTROL_DIR=$SCRATCH/control BLOCKLORE_ENV_FILE=$SCRATCH/env-target BLOCKLORE_SITE=http://localhost:3721 exec node --env-file-if-exists=.env brain/cli.ts daemon` (make `$SCRATCH/env-target` first with `install -m 600 /dev/null`; a subscription connect writes there instead of the real `.env`). It reads the real `var/review/` queue, so never approve or reject there.
- Production: https://blocklore.space/admin (or https://blocklore.vercel.app/admin), signed in with the owner's mail or `pnpm brain admin-link`.

## Gotchas

- React runs effects twice in dev. `/admin/auth` reads the token from the fragment and clears it; the second run must keep the first run's token (it does: `setToken((prev) => m?.[1] ?? prev ?? "")`). Same for any future fragment handoff.
- Next's route announcer has `role="alert"`, so a test that waits for "the" alert picks it up; wait for text instead.
- Relative times ("12 s ago") differ between the server render and the browser; render them with `<Ago>` (`suppressHydrationWarning`), or the dev overlay counts an issue.
- A command waits in `ctl:cmd` for the daemon and expires after 15 minutes. If the admin shows "Waiting for the brain to pick it up", look at `journalctl --user -u blocklore-brain -n 50`.
- Approve, reject, withdraw and "Evaluate now" act on the daemon's own checkout. Drive them only against a daemon run from a scratch clone ([review](review.md)), never the dev daemon above, which reads the real `var/review/`.
